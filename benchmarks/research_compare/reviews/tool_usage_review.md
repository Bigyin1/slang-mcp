All 18 completed project-load argument sets were inspected. Their 75 source-path entries and 16 include-directory entries, counting repeats, resolve inside the corresponding case/arm/repetition runtime workspace. They refer to supplied `rtl`, included `.bender` dependency subtrees, or `integration.sv`; there are no cross-run or outside-workspace loads. The 213 recorded treatment calls all target `slang`, and no source-only trace contains an MCP call. This is an audit of preserved command/MCP activity, not an operating-system read-isolation proof; shared startup instructions and the prompt-based read boundary remain the protocol's documented limitations.

The frozen instruction already asks for narrow queries, selected sections on `inspect_*`, aggregate instance facts, reuse, and exact returned identifiers: [skill lines 22–32](../skill.md#L22), [41–48](../skill.md#L41). These recommendations should not be presented as missing ideas in the current skill. The current [bulk tool schema](../../../src/contract.json#L277) does not expose `fields`, and [facts_for](../../../src/rtl_queries.cpp#L6) unconditionally computes and returns parameters plus connections. Its [named filter](../../../src/query.hpp#L28) treats an absent or null name list as all items, while an explicit empty list selects none. A future skill example could explain those existing empty-list semantics, but skipping a whole section and its computation requires an API addition; omitting a nonexistent `fields` option is not an instruction failure. Separately, “Use source inspection and MCP together throughout the task” at [skill line 4](../skill.md#L4) may encourage recurring confirmation despite the reuse rule. This is an instruction-design hypothesis, not an established cause of the observed calls. A future version could tie each tool use to missing required evidence, with no fixed alternation between source and MCP.

A separate [compiler-only payload probe](../payload_probe/README.md) verified those empty-filter semantics on the frozen binary and original inputs. The original probe used six semantic calls and zero model calls; a later verification replay used six more semantic calls and reproduced its metrics and projections. Both are excluded from the main-run counts. IDMA's structured response shrank from 23,565 to 2,595 canonical UTF-8 JSON bytes with `port_names=[]`; Floo's shrank from 18,094 to 16,582 bytes with `parameter_names=[]`. The requested section facts and instance/page identities were exactly equal before and after. These paired payload counterfactuals establish neither worker token/time savings nor an answer-quality effect. Their source-location path context differs from the worker traces, so the baseline byte counts are not directly comparable to the table above.

The observed duplication also has a concrete server origin: [successful_result in server.cpp](../../../src/server.cpp#L49) sets both structured content and a JSON text content item from the same payload. It is not something the worker can remove by narrowing its arguments, and changing the representation requires checking client compatibility and model-visible rendering. The report deliberately makes no double-billing claim.

For the two exact ambiguity triggers, the arguments were:

```json
{"identifier":"compare_idma_state.i_dataflow.data_i"}
{"identifier":"compare_idma_state.i_packet_fifo.usage_o"}
```

The [resolver](../../../src/adapters/design.cpp#L266) first checks stable IDs, then matches qualified or simple names across indexed kinds and rejects any match count other than one. [Symbol IDs include kind plus qualified path](../../../src/adapters/normalization.cpp#L59), while the [searchable kinds](../../../src/adapters/design.cpp#L14) include both ports and variables. A port and its internal signal sharing a path is therefore a plausible source-level explanation; candidate identities were not enumerated in these traces, so that specific pair remains an inference. An API change should preserve the distinction rather than silently choosing a kind. Returning candidate stable IDs in ambiguity diagnostics is a concrete option for review. Separately, [tool_error](../../../src/server.cpp#L21) sets the MCP error flag, while this CLI's sanitized event records the call as `status="failed"` and leaves its separate `error` field null; auditing must account for that representation.
