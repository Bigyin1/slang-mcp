# RTL versus RTL + MCP + instruction

Парное исследование C++ сервера от 15 ноября 2026 года. Сравниваются чтение
исходников и чтение тех же исходников с MCP и подробной инструкцией. Варианта
«MCP без инструкции» в этом исследовании нет.

Результат 28 рабочих прогонов зависит от задачи: на небольших вопросах
о фактах MCP не улучшил ответы, а в открытом ревью некорректного RTL
помог найти пропущенную ошибку порта и избежать ошибочных дополнительных
выводов. За это требовалось больше входного контекста. Ниже две серии
показаны раздельно; по наблюдениям уже уточнена инструкция и исправлена
навигация по экземплярам в C++ сервере.

## Результат основной серии

**На этих задачах превосходство MCP по качеству не подтвердилось.** Все
24 ответа получили 8/8 за запрошенные факты у обоих независимых рецензентов.
MCP с инструкцией потребовал больше токенов и в среднем больше времени.
Все запланированные попытки завершились; таймаутов, потерянных ответов и
неизвестных счётчиков в основной серии нет.

В каждом столбце ниже — 12 попыток: шесть задач по два повтора. Токены
суммируются по попыткам; время приведено на одну попытку.

MCP был медленнее в 10 из 12 пар. Два ускорения — AXI во втором повторе
и iDMA в первом — не повторились в другой попытке той же задачи. Это
описательные наблюдения, без утверждения о статистической значимости.

Оценки объяснений также совпали между рецензентами. Во всех ответах они
максимальны, кроме одного лишнего утверждения в первом MCP-ответе AXI:
фраза, что `i_wire` переопределяет «только Depth», игнорирует переданные
типовые параметры. Запрошенные факты остались правильными, но аккуратность
выводов получила 1/2 вместо 2/2. Эта оговорка сохранена, а не растворена
в общем фактическом балле.

Полные значения каждой попытки: [runs.tsv](results/runs.tsv).
Машиночитаемые метрики, парные разницы и проверки целостности:
[metrics.json](results/metrics.json). Все проверки полного экспорта прошли
(`complete`, `artifacts_complete`, `integrity_valid` равны `true`).
Сводка двух рецензентов: [main_scores.json](reviews/main_scores.json);
их отдельные оценки и основания сохранены рядом.

## Что видно в работе с инструментами

В основной серии зафиксированы 213 вызовов MCP и обращения ко всем 13
открытым инструментам. Шесть вызовов завершились ошибкой инструмента,
хотя сами рабочие попытки успешно закончились. Три ошибки относятся к
`list_symbols` на существующих путях экземпляров, две — к неоднозначным
именам портов, одна — к запросу отсутствующего внешнего экземпляра.
Сам факт вызова не доказывает необходимость инструмента: например,
все три попытки использовать `list_symbols` в этой серии были неуспешны.

MCP не заменил чтение RTL: в его группе было 80 shell-вызовов против 59
в группе исходников. Наблюдались повторное получение уже доступных
параметров, ненужные разделы агрегированных ответов и переключения
single-unit режима с повторными загрузками. Это конкретные направления
упрощения работы агента; их нельзя объяснять только числом инструментов.

Проверены все 139 shell-команд и пути всех 18 загрузок. Запрещённых
обращений к эталонам, внешним исходникам, вебу, другим компиляторам или
субагентам по этим командам не обнаружено. В группе исходников нет вызовов
MCP, все обращения MCP направлены серверу `slang`. Это проверка наблюдаемых
команд, а не утверждение об изоляции всей файловой системы.

Подробности, точные аргументы и ссылки на трассы:
[tool_usage_review.md](reviews/tool_usage_review.md). В сохранённом
представлении успешных ответов один JSON присутствует и в text content,
и в structured content. Из этого **не следует**, что модель получила или
оплатила обе копии: для такого вывода нужно отдельно проверить отображение
инструментов клиентом.

## Методика

Основная серия: шесть задач, два метода, два повтора — 24 независимых CLI-сеанса.
Четыре задачи используют закреплённые фрагменты CVA6, FlooNoC, AXI и iDMA;
две контрольные задачи проверяют single compilation unit/макросы и анализ
некорректного фрагмента с намеренно отсутствующей внешней зависимостью.
Каждому агенту доступна одинаковая копия исходников и конфигурации. Агент сам
выбирает файлы для загрузки; реальные проекты целиком не компилируются.

Условия, задания, исходники, критерии, инструкция, порядок запусков и runner
зафиксированы коммитом `9de333a` **до первого результата**. Порядок задач
перемешан с seed `20261115`; порядок методов внутри пары обращён во втором
повторе. Одновременно работают не более двух CLI-процессов. Один запуск
ограничен 600 секундами. Все попытки сохраняются; выборочных перезапусков нет.
См. [protocol.json](protocol.json), [manifest.json](manifest.json),
[inputs.json](inputs.json) и [skill.md](skill.md).

Рабочая модель — запрошенный идентификатор **`gpt-5.6-terra`, effort `max`**,
Codex CLI `0.153.3`. Запрос `gpt-6.1-terra` через этот CLI был отклонён
с `model_not_found`; поэтому это не результаты GPT‑6.1 Terra. Фактическую
внутреннюю маршрутизацию провайдера независимо проверить нельзя. Для обоих
методов модель и настройки одинаковы. Сервер собран из C++ версии `283faf6`;
SHA-256 использованного исполняемого файла:
`eeecb677599bdd6d4563776456d5ab52bad2b5f52a5154e39f2e7cc0c87bbd19`.

Два независимых исследовательских агента GPT‑6.1 Sol оценивают ответы по
заранее заданным исходникам и восьми критериям: 0, 0,5 или 1 балл за каждый.
Совпадение формулировки с эталоном не требуется; обычный текстовый ответ
принимается. Дополнительно и **отдельно от фактического балла** оцениваются
обоснование, полнота объяснения, проверяемость ссылок и аккуратность выводов
(каждая шкала 0–2). Рецензентам не показываются название метода, время,
токены и оценки друг друга. Маскирование частичное: сам ответ может упоминать
MCP. Сохранены обе исходные оценки и соответствие анонимных ID запускам.

## Как читать затраты

- `input_tokens` — суммарный вход по запросам внутри CLI-сеанса, включая
  повторную передачу контекста. Это не максимальный размер контекстного окна.
- `cached_input_tokens` — часть входа, обслуженная из кэша;
  `input_tokens - cached_input_tokens` приводится отдельно.
- `output_tokens` — сообщённый CLI выход;
  `reasoning_output_tokens` является его частью и повторно не прибавляется.
- Общий счётчик — `input_tokens + output_tokens`. Кэш и reasoning не
  складываются с ним повторно. Эти величины не переводятся в денежную стоимость.
- Время — монотонное время ожидания CLI-процесса с работой модели, MCP и
  инструментов. Подготовка копии файлов и сам `Popen` в него не входят.
  Время зависит от нагрузки сервиса, поэтому одиночная разница не является
  доказательством ускорения.

Источник токенов — реальные события `turn.completed`, не оценка по длине
ответа. Неизвестное значение остаётся `null`. Сырые события reasoning и stderr
не входят в публикуемые артефакты: сохраняются ответы, параметры запуска,
команды, вызовы MCP и счётчики. Перед экспортом проверяются хеши исходников,
бинарного файла, задания, инструкции и точных параметров каждого запуска.

## Границы выводов

Это небольшие фрагменты и сильная модель с высоким reasoning effort, а не
случайная выборка задач из промышленной разработки. Два повтора не являются
независимыми проектами. Результаты реальных RTL-фрагментов и искусственных
контролей следует рассматривать раздельно. Высокий балл обоих методов может
означать, что задача недостаточно трудна для обнаружения разницы.

Shell доступен обоим методам; другие компиляторы, веб и субагенты запрещены
заданием. Sandbox запрещает запись, но не изолирует все чтения хоста: ограничения
области чтения проверяются по публичным командам. `--ignore-user-config` не
устраняет общий стартовый текст AGENTS/skills, что отмечено в протоколе.
Исследование не измеряет отдельно эффект схем MCP и эффект инструкции.
Сравнение с обычным compiler CLI или другими MCP-серверами не проводилось.
Кэш провайдера между запусками не сбрасывался; порядок методов меняется,
но полной независимости кэша это не обеспечивает. Учёт затрат относится
к рабочим попыткам: подготовка корпуса, preflight и исследовательские
рецензенты в него не включены.

## Отдельная открытая серия

[open_review/protocol.json](open_review/protocol.json) и исходники зафиксированы
коммитом `ebd9989` до её запусков. Две задачи × два метода × один повтор —
ещё четыре попытки с тем же сервером, моделью и исходной инструкцией.
Серия начинается после завершения основной, сохраняя ограничение параллелизма.

Здесь требуется обычное инженерное ревью AXI и iDMA по заданному контракту.
В каждом фрагменте есть намеренно внесённые ошибки компиляции и поведения,
а также объявленная отсутствующая внешняя зависимость. Число ошибок и их
места агенту не сообщаются. Ошибки принадлежат benchmark-корпусу — это
**не сообщение об ошибках upstream-проектов**. Критерии написаны по исходникам
до проверок компилятором; независимое ревью подтвердило мутации, границы
частичного анализа и одинаковость входов двух методов.

Эта серия запланирована после первых равных оценок основной серии, поэтому
является разведочной. Она не смешивается с исходными 24 попытками и не
служит независимым подтверждением заранее выбранной гипотезы. После её
результатов дополнительные случаи ради получения положительного эффекта
не подбираются. См. [описание корпуса](open_review/README.md) и
[проверку источников](open_review/review.json).

### Результаты открытого ревью

Все четыре попытки завершились с ответами и полными счётчиками. **На этих
двух ревью некорректных фрагментов MCP дал более полные и аккуратные
ответы**, хотя потребовал больше входного контекста. Оба метода работали
с теми же намеренно неполными проектами, без реализации внешнего монитора.

| Фрагмент / метод | Итоговый балл / 8 | Время, с | Вход (из него кэш) | Выход (из него reasoning) |
| --- | ---: | ---: | ---: | ---: |
| AXI / исходники | 7,5 | 269,6 | 165 773 (114 176) | 10 611 (8 023) |
| AXI / MCP + инструкция | 8 | 360,8 | 897 004 (833 792) | 13 417 (9 689) |
| iDMA / исходники | 6 | 542,2 | 98 753 (71 168) | 21 836 (19 380) |
| iDMA / MCP + инструкция | 8 | 559,1 | 703 970 (619 520) | 21 828 (17 080) |

В **AXI оба метода нашли все три внесённых дефекта и правильные минимальные
исправления**. Но ответ по исходникам ошибочно объявил `fifo_v3` отсутствующим,
хотя реализация находилась в поставленном `.bender`-каталоге, и назвал весь
W-channel struct 128-битным вместо 150-битного. Ответ с MCP избежал этих
дополнительных ошибок. Это преимущество в полноте проверки зависимостей и
точности объяснения, а не дополнительный найденный основной дефект.

Рецензенты дали первому AXI-ответу 7 и 7,5: они согласились с обеими ошибками,
но по-разному учли лишнее утверждение о ширине. При разборе сохранены 7,5,
поскольку A4 требует правильного объяснения type/value и ремонта `w_chan_t`,
а точный битовый размер в нём явно необязателен. Ошибка ширины остаётся
в оценке объяснения; ложная граница отсутствующей зависимости снижает A8.
Исходные оценки и открыто обозначенное неслепое разрешение разногласия
сохранены в [open_adjudications.json](reviews/open_adjudications.json).

В **iDMA MCP нашёл все три дефекта, а исходники — два**. Пропущен ошибочный
именованный порт `.ready_out` вместо существующего `ready_o` в generated
lane FIFO. Оба ответа правильно нашли value/type ошибку packet FIFO,
неправильную очистку памяти при flush и отделили отсутствующий монитор
от локальных проблем. Дополнительное рассуждение исходного агента об
атомарности lanes было явно условным; его не штрафовали как ложный дефект.

В сумме этой отдельной серии: 13,5/16 против 16/16; найдено 5/6 против
6/6 внесённых локальных дефектов. Вход без кэша — 79 182 против 147 662
токенов (1,86×), выход — 32 447 против 35 245 (1,09×). Сумма времён попыток
выросла на 13,3%. Это два специально подготовленных случая с одним повтором,
не оценка средней эффективности на промышленной выборке.

[Полные метрики](open_results/metrics.json), [таблица попыток](open_results/runs.tsv),
[оценки](reviews/open_scores.json), [проверка вызовов](reviews/open_tool_usage_review.md).
Все проверки целостности экспорта прошли. Проверка 52 shell-команд выявила
одну вспомогательную попытку `git status` в AXI-группе исходников, выходившую
за узкую категорию чтения RTL/арифметики; её сохранённый вывод пуст.
Обращения к эталонам или внешние данные в трассе не обнаружены. Попытка
сохранена и явно отмечена, а не исключена после просмотра результата.

Практическая гипотеза для следующего применения: при ревью поломок сначала
загружать небольшой нужный фрагмент и читать диагностики, затем обращаться
к RTL для поведения и намерений. На небольших фактологических вопросах
добавочные подтверждающие запросы могут лишь увеличивать затраты.
Этому соответствует уточнение общей инструкции; её новая версия ещё
не проходила рабочее сравнение.

## Проверенное сокращение ответов и новая инструкция

Разбор вызовов обнаружил исправимую причину больших ответов. У
`list_instance_facts` пропущенный фильтр имён возвращает все факты раздела,
а пустой список выбирает ноль фактов. В отличие от `inspect_instance`,
этот инструмент не поддерживает `fields`. Поэтому для запроса только
параметров следует передать `port_names=[]`, а для запроса только соединений —
`parameter_names=[]`. Оболочка страницы остаётся в ответе; вычисление
ненужного раздела внутри сервера эта фильтрация не устраняет.

Отдельная проверка на том же бинарном файле — два `project_load` и четыре
запроса, **без обращений к модели** — дала:

| Запрос | Исходный ответ, байт | С пустым фильтром, байт | Сокращение |
| --- | ---: | ---: | ---: |
| Параметры экземпляров iDMA | 23 565 | 2 595 | 88,99% |
| Соединения `clr_i` в Floo | 18 094 | 16 582 | 8,36% |

Запрошенные факты, идентификаторы экземпляров и внешняя пагинация совпали
точно. Это размеры канонического structured JSON внутри каждой пары
проверки; формат путей зависит от рабочего каталога. Это **не измерение
снижения токенов или времени рабочего агента**. Воспроизводимые аргументы,
ответы, хеши и ограничения находятся в [payload_probe](payload_probe/README.md).

На основании наблюдений обновлена [общая инструкция](../skills/semantic.md)
для будущих запусков: добавлены явные пустые фильтры, группировка запросов
по конфигурации компиляции и условие остановки после получения достаточных
данных. Убрано требование чередовать исходники и MCP на протяжении всей
задачи. Неоднозначные символы предлагается разрешать через возвращённый
`symbol_id`. **Обе текущие серии используют прежнюю зафиксированную
[инструкцию](skill.md)**; эффект новой версии на ответы и затраты модели
в этом исследовании не измерялся.

## Исправление навигации после измерений

В C++ адаптере исправлен `list_symbols`: точный путь вложенного экземпляра
или generate-области теперь можно передать как `scope`. Раньше путь,
полученный из иерархии и принимаемый `inspect_instance`, мог завершаться
`unknown symbol`. Используется существующий индекс иерархии Slang;
новых методов или полей API не добавлено. Сохраняются прямые члены области,
стабильные ID, фильтрация и пагинация. Имя модуля, в том числе совпадающее
с путём верхнего экземпляра, сохраняет трактовку declaration defaults.

Повторены три действительно неудачных запроса из основной серии с исходным
выбором файлов. После исправления они вернули 39, 32 и 39 членов нужных
областей. В Floo при этом сохранились 15 диагностических ошибок исходной
частичной загрузки: успешная локальная навигация не выдаётся за полную
корректность проекта. [Доказательство до/после](scope_fix/proof.json),
[вызовы](scope_fix/replay.calls.jsonl),
[независимое ревью](reviews/scope_fix_review.json).

`make check-all` прошёл: форматирование, строгий линтер, ограничение
сложности, native-тесты, 136 benchmark-тестов и real-world preflight.
Рецензент независимо проверил 53 утверждения в трёх регрессионных случаях.
Preflight сохраняет диагностики RTL; он не означает, что все внешние
дизайны компилируются без ошибок. [Хеши и проверки](scope_fix/build_identity.json).

Исправление выполнено **после основной серии**. Обе серии рабочих ответов
используют прежний сохранённый бинарный файл; новую версию проверяли только
функционально. Ей не приписывается измеренное улучшение качества, времени
или токенов агента.

## Воспроизведение

Сначала соберите сервер и установите существующее benchmark-окружение:

```sh
uv sync --project benchmarks --python 3.10
```

`manifest.json` сохраняет абсолютные пути исходного запуска. Для нового
эксперимента создайте отдельный manifest с локальными путями к CLI, бинарному
файлу, инструкции и входным каталогам. Исходный manifest не редактируйте.
Публичный состав каждого каталога перечислен в `inputs.json`: скопируйте
соответствующие файлы из `cases/<case>/`, а `config.json` запишите из поля
`config` (`json.dumps(..., indent=2) + "\n"`). Проверьте SHA-256 всех файлов
по полю `files`. Не копируйте в рабочие каталоги oracle, provenance, отчёты
или результаты. Для отдельной открытой серии есть собственный materializer.

```sh
benchmarks/.venv/bin/python -m benchmarks.research_compare run \
  --manifest /path/to/new-manifest.json --output /path/to/new-runs --jobs 2
```

Эта команда выполняет реальные обращения к модели. Перед ними зафиксируйте
новый протокол и входы. Существующий каталог попыток runner не перезаписывает.
Для аудита именно исходной серии на исходной машине:

```sh
benchmarks/.venv/bin/python -m benchmarks.research_compare.audit \
  --runs /private/tmp/slang-compare/runs --output /path/to/new-export
```

Аудит привязан к коммиту заморозки; он намеренно не считает изменённые пути,
исходники или бинарный файл точным повторением исходного запуска.
