# slang-mcp

## Назначение и ограничения проекта

- Это read-only MCP-сервер для семантического анализа SystemVerilog-проектов через
  `pyslang`. Сервер не изменяет RTL, не является LSP и не строит regex-парсер или
  псевдонетлист.
- Проект должен оставаться совместимым с CPython 3.10. Используйте окружение из
  `uv.lock`, создаваемое командой `uv sync --python 3.10`.
- Зафиксированная версия bindings — `pyslang==11.0.0`. В этой версии API разделён
  между пространствами имён `pyslang.ast`, `pyslang.parsing` и `pyslang.syntax`;
  не предполагайте, что AST и parser-классы экспортируются из корня `pyslang`.
- Используйте Python API Slang, а не запуск исполняемого файла Slang как subprocess.

## Архитектурные границы

- MCP handlers должны оставаться тонкими и вызывать `SemanticService`.
- Жизненным циклом активной компиляции управляет `ProjectManager`.
- Источник build-конфигурации скрыт за `ProjectProvider`; MVP использует
  `StaticProjectProvider`. Не добавляйте фиктивный `SVBuildProjectProvider`.
- Динамические объекты `pyslang` не должны выходить за границы
  `src/slang_mcp/adapters/`. В сервисах и MCP-ответах используйте только
  типизированные project-owned модели.
- Различайте `logical_module` (сущность build-системы), `sv_module` (декларация
  SystemVerilog module) и `instance` (элаборированный экземпляр).
- Полная connectivity-трассировка остаётся вне MVP; не заменяйте её анализом текста RTL.
- RTL read/write и driver/load запросы описывают source-level семантику, не netlist.
  Используйте встроенный visitor Slang и общий индекс обращений.
- При reload диагностические ошибки принимаются для анализа; исключение при построении
  не должно менять активную компиляцию и последние semantic snapshots.
- Для сложных операций предпочитайте подходящие готовые библиотеки: обход Slang AST —
  встроенный visitor; работа с Git в real-world тестах — GitPython.

## Проверки

- `make check` запускает проверку форматирования, Ruff, Pylint с настроенными extensions,
  strict mypy, Xenon, unit и integration тесты.
- `make check-all` дополнительно запускает opt-in real-world тесты на закреплённых ревизиях
  PULP `common_cells` и `axi`. Тесты используют Bender `0.32.1` для генерации sources, include
  dirs и defines и могут потребовать сеть при отсутствии локального кэша. Транзитивные
  зависимости `axi` закреплены отдельным Bender lockfile в `tests/realworld`.
- Перед завершением изменения запускайте проверки, относящиеся к его области. Для изменений
  production-кода или зависимостей запускайте `make check-all`, если внешнее окружение доступно.
- При изменении зависимостей в `pyproject.toml` обязательно обновляйте `uv.lock`.

## Неоднозначные ситуации и вопросы разработчику

Вопрос разработчику обязателен, если разумные варианты решения приводят к разному внешнему
поведению, формату данных, публичному API, совместимости или риску потери данных. Не выбирайте
молча вариант, который трудно отменить.

## Работа с Git

1. Перед изменениями выполните `git status --short` и учитывайте уже существующие изменения.
   Считайте незнакомые изменения работой разработчика или другого агента.
2. Не откатывайте, не перезаписывайте и не форматируйте несвязанные пользовательские
   изменения.
3. Не применяйте `git reset --hard`, `git clean`, принудительный checkout/restore или другие
   разрушительные команды без явного запроса разработчика.
4. Агент может самостоятельно создавать локальные коммиты для полностью завершённых и
   проверенных изменений, если это не противоречит прямому указанию разработчика. Отдельное
   разрешение на каждый `git commit` не требуется.
5. Перед самостоятельным коммитом просмотрите diff, запустите относящиеся к задаче проверки
   и убедитесь, что коммит представляет одну законченную логическую правку. Сообщение коммита
   должно кратко и точно описывать изменение.
6. Включайте в коммит только относящиеся к задаче файлы. Не используйте `git add .`, если в
   рабочем дереве есть посторонние изменения, и не захватывайте уже подготовленные кем-либо
   изменения без проверки staged diff.
7. Не выполняйте `git amend`, rebase, merge, push, force-push и не создавайте теги без
   явного запроса разработчика. Возможность самостоятельно создать локальный коммит не даёт
   разрешения публиковать его или переписывать историю.
8. Не обходите pre-commit hooks через `--no-verify`. Если проверка не проходит, исправьте
   причину или сообщите разработчику о блокере.
9. Не меняйте историю общей ветки. Для потенциально конфликтной операции сначала уточните
   ожидаемую ветку и стратегию интеграции.
10. Перед передачей результата проверьте `git diff` и `git status --short`, чтобы не включить
   временные файлы, секреты и несвязанные правки.
11. Обновление `uv.lock` обязательно при изменении зависимостей в `pyproject.toml`.
